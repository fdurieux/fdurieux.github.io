# Primary-source research notes

Accessed 28 October 2026. These are scoped paraphrases used in developing the model, not copies of the sources or a systematic literature review. Follow the URLs for independent verification and record any subsequent change.

| Source | What it supports | What it does not establish |
| --- | --- | --- |
| S4 — [DORA metrics](https://dora.dev/guides/dora-metrics/) | Five delivery-performance metrics; service-level measurement and defined event boundaries. Change lead time starts at code commit; failed-deployment recovery concerns failures requiring intervention; deployment rework concerns unplanned deployments resulting from production incidents. | A comprehensive software-quality score, all incident recovery, or a guaranteed result from upstream linting. |
| S5 — [Documentation quality](https://dora.dev/capabilities/documentation-quality/) | Documentation quality relates to technical capabilities and organizational outcomes; useful, maintained information matters. | A measured effect for every inventory tool, a particular lint rule or this whole causal graph. |
| S6 — [Continuous integration](https://dora.dev/capabilities/continuous-integration/) | Frequent integration, automated checks and prompt feedback support discovering problems while changes remain manageable. | A proof that a syntactic or structural check verifies intended behaviour. |
| S7 — [Small batches](https://dora.dev/capabilities/working-in-small-batches/) | Smaller units of work can shorten feedback and support learning; batch size is a relevant delivery mechanism. | A calibrated coefficient from gate waiting time to failure rate in this setting. |
| S8 — [Streamlining change approval](https://dora.dev/capabilities/streamlining-change-approval/) | Approval design and delay matter; more heavyweight approval is not automatically safer. | Proof that every gate is harmful or that the exact local R3 feedback loop has been observed. |
| S10 — [Test automation](https://dora.dev/capabilities/test-automation/) | Effective, maintainable automated tests and relevant user journeys are important delivery capabilities. | That passing Gherkin lint, or generating tests from the same mistaken specification as code, establishes correctness. |
| S11 — [NASA requirements management](https://www.nasa.gov/reference/6-2-requirements-management/) | Requirements dependencies, bidirectional traceability and change-impact analysis across design, interfaces, tests and operations. Later requirement changes can affect wider cost and schedule commitments. | A universal exponential defect-cost curve, a measured amplification factor for this inventory, or an empirical DORA result. This is engineering guidance. |

The proposed full cascade combines these sources with bounded pumllint evidence and causal reasoning. It remains a hypothesis requiring local validation. Related capability evidence does not validate every edge or feedback loop that uses it.
